# KB 智能路由 — 方案讨论

> 状态：📋 讨论中 | 创建：2026-06-01

## 问题

当前对话固定走一个 KB（session.kb_id 或默认 id=1），用户需手动切换知识库。聊天页 header 显示「关联 N 个本地知识库」会误导用户以为跨库检索。

## 目标

两层设计：用户可主动选 KB，不选时系统自动判断。

```
用户点「附加知识库」选了一个 KB → 直接用，不走自动匹配
       ↓ 没选（默认"自动"模式）
三层降级匹配 → 自动选出最佳 KB
```

## 匹配方法讨论

### 为什么不用描述匹配

KB 描述（"存放 Python 技术文档"）和用户提问（"GIL 锁怎么解决"）是**不同语义空间**的文本——一个是分类标签，一个是具体问题。余弦相似度在这两类文本之间不可靠。

### 推荐：KB 质心向量匹配

**每个 KB 维护一个质心向量**——该 KB 所有 chunk embedding 的均值：

```
KB 质心 = AVG(chunk_1, chunk_2, ..., chunk_n)
```

匹配时只做一次 pgvector 查询：

```sql
-- N 个 KB，1 次查询，< 1ms
SELECT id, centroid <=> question_embedding AS dist
FROM kb_knowledge_bases
ORDER BY dist LIMIT 1
```

为什么可靠：质心和问题在同一个语义空间——都是具体内容向量。一个写满 AI 论文但叫「项目资料」的 KB，质心就是 AI 论文的，用户问 LLM 问题时自然匹配上。

### 性能

| 环节 | 耗时 | 说明 |
|------|------|------|
| 查询匹配（10 个 KB） | < 1ms | pgvector `<=>` 余弦距离 |
| 质心更新 | ~50ms | 文档变动时异步执行，不影响提问 |
| Redis 缓存（可选） | TTL 10min | 质心向量缓存，直接跳过 DB |

**每次提问的额外延迟 ≈ 0**。质心是预计算好的，不实时扫描 chunk。

## Phase 2：自动匹配（KB 质心向量）

> 当用户选「自动」或 `kb_id=0` 时触发。

### 流程

```
问题 embedding
     │
     ▼
┌─ 质心匹配 ───────────────────────────────────────┐
│ SELECT id, centroid <=> question_embedding AS dist │
│ FROM kb_knowledge_bases ORDER BY dist LIMIT 1      │
│                                                    │
│ 最高分 ≥ 阈值(0.4) → 选中                          │
│ < 0.4 或无文档 KB → 回退默认 KB                     │
└──────────────────────────────────────────────────┘
    耗时：< 1ms
```

一层就够。质心和问题在同一语义空间，不需要描述做中间层。

### 质心维护

```
kb_knowledge_bases
  + centroid_embedding  vector(1024)   ← 新增
  + centroid_updated_at  timestamp    ← 新增

文档上传/删除/重索引时异步更新：
  centroid = AVG(SELECT embedding FROM kb_chunks WHERE kb_id = $1)
```

- **有小开销的场景**：用户上传文档后，触发一次 AVG 计算（~50ms），之后的提问查询免费
- **缓存**：Redis 存质心向量，TTL 10min，文档变动时失效

### 冷 KB 降级

KB 无 chunk → 质心为空 → 匹配时跳过 → 回退默认 KB (id=1)

### 全文检索兜底（可选后续）

如果质心匹配低置信度（< 0.3），可降级用 BM25/tsvector 做关键词匹配 KB 名+描述，或直接用默认 KB。
