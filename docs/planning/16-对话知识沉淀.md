# 对话知识沉淀 — 方案设计

> 状态：✅ 方案已确定 | 创建：2026-06-02

## 问题

当前 QA 流程是单向管道：用户提问 → 检索 → LLM 生成 → 存入 `kb_qa_records` → 结束。有价值的回答没有被反向沉淀到知识库，下次类似问题无法直接命中这些"已解答过"的知识。

## 目标

```
用户提问 → 检索 chunk → LLM 生成回答 → 存入 kb_qa_records
                                              │
                                              ▼ (定时批处理)
                                     LLM 二次提炼 → 知识点
                                              │
                                              ▼ (用户审核)
                                     kb_insights（可检索）
                                              │
                                              ▼
                                     下次提问 → 命中已提炼的知识
```

---

## 关键设计决策

| 决策点 | 结论 |
|--------|------|
| 沉淀内容 | **LLM 二次提炼**：从 QA 对话中提取独立知识点，非整段 QA 原文 |
| 触发时机 | **定时批处理**（如每日凌晨 2:00），不阻塞问答流程 |
| 去重策略 | **ID 溯源去重**（同一 QA 不重复提炼）+ **向量相似度**（和已有 insight 去重） |
| 审核机制 | 提炼后进入待审核队列，**用户审核**通过后入库 |
| 存储表 | **独立表 `kb_insights`**，长远考虑方便扩展为知识沉淀模块 |

## 数据库设计

### `kb_insights` 表

```sql
CREATE TABLE kb_insights (
    id              BIGSERIAL PRIMARY KEY,
    kb_id           BIGINT NOT NULL REFERENCES kb_knowledge_bases(id) ON DELETE CASCADE,
    
    -- 知识点内容
    title           VARCHAR(255) NOT NULL,          -- 知识点标题（LLM 提炼）
    content         TEXT NOT NULL,                   -- 知识点正文
    embedding       vector(1024),                   -- 向量，用于检索
    
    -- 溯源
    source_qa_ids   BIGINT[] NOT NULL,              -- 来源 QA 记录 ID 数组
    source_doc_ids  BIGINT[],                        -- 引用的文档 ID
    
    -- 审核状态
    status          VARCHAR(20) NOT NULL DEFAULT 'pending',  -- pending / approved / rejected
    reviewed_at     TIMESTAMPTZ,                    -- 审核时间
    
    -- 元数据
    confidence      FLOAT NOT NULL DEFAULT 0.0,     -- LLM 提炼时的置信度
    tags            VARCHAR(50)[],                   -- 自动标签
    
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_insights_kb ON kb_insights(kb_id);
CREATE INDEX idx_insights_status ON kb_insights(status);
CREATE INDEX idx_insights_embedding_hnsw ON kb_insights
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 200);
```

### 字段说明

| 字段 | 说明 |
|------|------|
| `title` | LLM 从 QA 中提炼的知识点标题，如 "CPython GIL 限制及解决方案" |
| `content` | 知识点正文，自包含，脱离原始对话也能读懂 |
| `embedding` | 用于向量检索，和 `kb_chunks` 在同一语义空间 |
| `source_qa_ids` | 追溯原始对话，用户可以点回去看完整上下文 |
| `source_doc_ids` | 原始回答引用了哪些文档 |
| `status` | `pending`(待审核) / `approved`(已入库) / `rejected`(已拒绝) |
| `confidence` | LLM 提炼时自评的置信度，辅助用户审核决策 |
| `tags` | LLM 自动打的标签，如 `["python", "GIL", "多线程"]` |

## 提炼流程

### 批处理任务（定时触发）

```
每日凌晨 2:00 或用户配置的时间
    │
    ▼
┌─ Step 1：提取未处理的 QA ──────────────────────────────┐
│                                                        │
│  SELECT * FROM kb_qa_records                           │
│  WHERE id NOT IN (SELECT unnest(source_qa_ids)          │
│                   FROM kb_insights)                     │
│  AND created_at > (NOW() - INTERVAL '24 hours')         │
│  AND LENGTH(answer) > 200   -- 太短的回答不值得提炼     │
│                                                        │
└────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 2：LLM 二次提炼 ─────────────────────────────────┐
│                                                        │
│  使用和问答相同的 LLM provider/model，temperature=0      │
│  非流式，批量处理（一次调用处理 N 条 QA）                 │
│                                                        │
│  System Prompt:                                         │
│  "你是一个知识提炼助手。请从以下对话中提取独立、自包含    │
│   的知识点，以 JSON 数组返回。要求：                      │
│   1. 每个知识点有独立标题，脱离对话也能读懂               │
│   2. 保留所有关键信息，不丢失细节                         │
│   3. 如果对话太浅或信息量不足，跳过不提炼                 │
│   4. 标注每个知识点的置信度(0-1)"                        │
│                                                        │
│  User Prompt:                                           │
│    以下是今日的用户对话，请提炼知识点：                    │
│    1. Q: "GIL 锁怎么解决？"                              │
│       A: "GIL 是 CPython..."                             │
│    2. Q: "Django ORM 和 SQLAlchemy 区别？"               │
│       A: "Django ORM 是..."                              │
│                                                        │
│  返回格式:                                               │
│  [{                                                     │
│    "title": "CPython GIL 限制及解决方案",                 │
│    "content": "CPython 的 GIL...",                       │
│    "confidence": 0.9,                                    │
│    "tags": ["python", "GIL", "多线程"],                   │
│    "source_qa_ids": [1]                                  │
│  }, ...]                                                │
└────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 3：去重 ─────────────────────────────────────────┐
│                                                        │
│  ID 去重：同一 source_qa_id 已提炼过 → 跳过             │
│  向量去重：新知识点 embedding 和已有 approved insight   │
│           做余弦相似度，> 0.92 → 标记为重复，跳过         │
│                                                        │
└────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 4：写入 kb_insights（status=pending）────────────┐
│                                                        │
│  为新知识点生成 embedding，写入 kb_insights              │
│  状态为 pending，等待用户审核                            │
│                                                        │
└────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 5：通知用户 ─────────────────────────────────────┐
│                                                        │
│  前端通知中心显示：                                      │
│  "昨日对话已提炼 5 条知识点，待审核"                      │
│  点击进入审核页面                                        │
└────────────────────────────────────────────────────────┘
```

### 手动触发

用户在对话页对某条回答点「保存到知识库」→ 即时触发该条 QA 的提炼，跳过批处理队列。

## 检索集成

`kb_insights` 中的知识点参与检索，和 `kb_chunks` 在同一语义空间：

```sql
-- 联合检索：chunks + insights
(SELECT
    c.id AS chunk_id,
    d.doc_name AS source,
    c.content,
    1 - (c.embedding <=> :query_vec) AS similarity,
    'chunk' AS result_type
 FROM kb_chunks c
 JOIN kb_documents d ON c.document_id = d.id
 WHERE d.deleted_at IS NULL AND d.status = 2 AND d.kb_id = :kb_id
   AND 1 - (c.embedding <=> :query_vec) >= :threshold)

UNION ALL

(SELECT
    i.id AS chunk_id,
    i.title AS source,
    i.content,
    1 - (i.embedding <=> :query_vec) AS similarity,
    'insight' AS result_type
 FROM kb_insights i
 WHERE i.status = 'approved' AND i.kb_id = :kb_id
   AND 1 - (i.embedding <=> :query_vec) >= :threshold)

ORDER BY similarity DESC
LIMIT :top_k;
```

在回答中标注来源类型：
- `📄 文档: xxx.md` — 来自上传文档
- `💡 知识沉淀: CPython GIL 限制及解决方案` — 来自对话提炼

## 监控埋点

> 详细设计见 [[21-监控告警系统]]

| event | status | 触发条件 |
|-------|--------|---------|
| `insight_batch_started` | success | 批处理开始 |
| `insight_batch_completed` | success | 批处理完成，记录提炼/跳过/去重数量 |
| `insight_batch_failed` | failed | 批处理失败 |
| `insight_llm_failed` | failed | LLM 提炼调用失败 |
| `insight_approved` | success | 用户审核通过 |
| `insight_rejected` | success | 用户审核拒绝 |
| `insight_assigned` | success | 知识点分配至目标 KB |

## 配置项

放在 `system_config` 或 `kb_config` 中：

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `insight_extraction_enabled` | `true` | 是否启用对话知识提炼 |
| `insight_extraction_schedule` | `"02:00"` | 批处理触发时间 |
| `insight_min_answer_length` | `200` | 答案最少字符数，短答案跳过 |
| `insight_dedup_threshold` | `0.92` | 向量去重阈值 |
| `insight_auto_approve_confidence` | `0.95` | 超过此置信度自动通过（跳过审核） |
