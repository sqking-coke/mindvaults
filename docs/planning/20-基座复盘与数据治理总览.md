## 一、基座能力复盘

### 1.1 当前基座全景

```
┌─ 输入 ──────────────────────────────────────────────────┐
│  文档上传  │  Obsidian Vault 导入  │  (外部对话 — 暂无)   │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 摄入管道 ──────────────────────────────────────────────┐
│  parser → chunker → embedder → kb_chunks                 │
│  ✅ 稳定，支持 PDF/Word/MD/TXT，1024 维 pgvector HNSW    │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 检索 + 问答 ───────────────────────────────────────────┐
│  embed(question) → vector search → reranker → LLM → 回答 │
│  ✅ SSE 流式，thinking 过程可见，引用溯源                  │
│  ⚠️ 当前固定单 KB，无智能路由                             │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 存储 ──────────────────────────────────────────────────┐
│  kb_qa_records  ← 问答日志（单向写入，从未回读利用）       │
│  ❌ 没有反馈回路 → 知识库只进不出                         │
└──────────────────────────────────────────────────────────┘
```

### 1.2 逐层评估

| 层 | 现状 | 评分 | 缺口 |
|----|------|:----:|------|
| **摄入管道** | parser/chunker/embedder 完整，支持多格式 | 🟢 牢固 | 摄入后无概念抽取、无重复检测 |
| **检索管道** | pgvector HNSW + Redis 缓存 + Reranker | 🟢 牢固 | 单体函数，不支持联合检索（chunk + insight）、无概念注入、无状态过滤 |
| **问答管道** | SSE 全流程 + thinking 流 + 引用溯源 | 🟢 牢固 | kb_id 固定，无智能路由 |
| **多 KB 管理** | kb_knowledge_bases + kb_config + kb_id 隔离 | 🟢 牢固 | 缺 kb_type 区分（普通/沉淀） |
| **配置管理** | system_config (全局) + kb_config (按 KB) | 🟢 牢固 | 阈值字段需随新功能扩展 |
| **数据模型** | 10 张表，ORM + Pydantic Schema + Alembic 迁移 | 🟢 牢固 | kb_chunks 无生命周期字段（status/source_type/quality_score） |
| **异步/后台任务** | ❌ 不存在 | 🔴 缺失 | 定时提炼、定期扫描、质心异步更新都依赖此能力 |
| **API 鉴权** | 无（当前不需要登录） | 🟡 可接受 | Skill 外部推送需要 KB 级 API Key + 中间件 |
| **前端路由** | 4 个主面板，路由平铺 | 🟡 可扩展 | 新增数据治理面板 + 子路由（/kb/manage/*） |

### 1.3 最关键的三个缺口

**缺口 1：没有后台任务系统**

五个新方案中，#15（质心异步更新）、#16（定时提炼）、#19（定期扫描）都需要后台任务调度。当前后端只有一个 FastAPI 进程，没有 worker/scheduler。

影响：这些功能要么同步执行阻塞请求，要么无法落地。

**缺口 2：没有 API Key 认证机制**

#17 Skill 集成需要外部 LLM 平台推送数据到 mindvaults。当前 `deps.py` 仅支持全局 Bearer token 鉴权，API_KEY 为空或默认值时完全放行，且用裸 `HTTPException`（违反 #14 异常规范）。必须增加 KB 级 API Key 生成 + 验证中间件。

影响：Skill 集成无法上线，安全风险。

**缺口 3：kb_chunks 没有生命周期管理**

Chunk 从创建到删除，没有状态流转（active/superseded/orphan）。#19 的去重合并需要标记旧 chunk 为 superseded，#16 的 insight 入库需要标记 source_type。这些字段缺失意味着治理操作没有落地载体。

影响：#16 和 #19 的写入操作缺少数据模型支撑。

### 1.4 源码审查 — 发现的 Bug

> 审查日期：2026-06-03 | 范围：全量源码 vs 设计文档交叉比对

**Bug 1：`chat_service.py:delete_session` — QA 记录被删除两次**

```python
# 第一次删除（行 430-432）
await db.execute(
    delete(KbQaRecord).where(KbQaRecord.session_id == session.id)

# 然后 count 查询（行 434-438）— 此时已删光，永远返回 0
qa_count = (await db.execute(
    select(func.count()).select_from(KbQaRecord).where(KbQaRecord.session_id == session.id)

# 第二次删除（行 441-443）— 空操作，浪费一次 DB round-trip
await db.execute(
    delete(KbQaRecord).where(KbQaRecord.session_id == session.id)
)
```

修复：先 count 再 delete，去掉第二次 delete。

**Bug 2：`retrieval_service.py:get_config_by_kb` — getter 有副作用**

```python
# 当 KB 不存在时自动创建 KB + 配置（行 26-30）
kb = (await db.execute(select(KnowledgeBase).where(KnowledgeBase.id == kb_id))).scalar_one_or_none()

    await db.flush()
```

`retrieve_chunks(kb_id=0)` → `get_config_by_kb(db, max(0, 1))` = `get_config_by_kb(db, 1)`，但如果传入不存在的 kb_id，getter 会静默创建 KB。调用方不期望此副作用。

修复：getter 只读取，不存在时抛 `KbNotFoundError`。`kb_service.get_kb_config` 已有正确的懒创建逻辑。

**Bug 3：`chat_service.py` — `system_prompt` 硬编码未读 DB**


`system_config.system_prompt` 字段已存在，但 `chat_stream` 从未读取。用户通过设置页面修改的 system_prompt 不会生效。

### 1.5 源码审查 — 代码质量问题

**问题 1：Embedding 配置解析逻辑重复（DRY 违规）**

`chat_service.py:106-134` 和 `ingestion_service.py:80-96` 包含几乎相同的 embedding provider/key/url 解析逻辑（约 25 行）。应抽取为 `embedding_service.py` 中的 `resolve_embedding_config()` 公共函数。

**问题 2：`chat_service.py` 过于庞大（558 行）**

混合了：会话管理、意图分类、检索编排、LLM 调用、QA 记录写入、历史查询、会话列表、会话删除。建议按职责拆分：
- `chat_service.py` — 核心问答流（chat_stream + 辅助函数）
- `session_service.py` — 会话 CRUD（list_sessions, delete_session, get_chat_history）

**问题 3：前端日期格式违反 CLAUDE.md**

`mindvaultsContext.tsx:571`：
```typescript
const now = new Date().toISOString().replace("T", " ").substring(0, 16);
```
CLAUDE.md 规定：「统一使用 `src/utils/date.ts` 中的工具函数，不手写 `.substring()` 或 `.replace("T"," ")`」

**问题 4：`mindvaultsContext.tsx` 过大（833 行）**

一个 Context 承载：会话管理、KB 管理、文档管理、系统配置、Vault 导入、Toast 通知、长轮询。建议拆分为多个 Context（`ChatContext`、`KbContext`、`SystemConfigContext`）。

## 二、数据治理系统总览

### 2.1 一句话定义

**数据治理系统把 mindvaults 从"单向检索管道"变成"知识闭环"**：对话中产生的价值回流到知识库，知识库的内容质量被持续监控和优化，概念网络让知识从孤立的片段变成可导航的图谱。

### 2.2 为什么要做

```
当前问题：

1. 知识只进不出
   上传文档 → 检索 → 回答 → 结束
   LLM 结合多份文档产生的优质回答，用一次就丢了

2. 知识质量退化
   - 重复内容占了检索位（同一知识点出现在 3 个 chunk）
   - 短 chunk 没有信息量但被检索命中
   - 旧版本内容没标记，LLM 可能引用过时信息

3. 知识之间没有关联
   - "质心向量匹配"出现在 5 个文档里，但没有统一定义
   - 用户读到术语不理解，得离开系统去搜索

4. 外部对话无法回流
   - 用户在 Claude Code 里聊的内容，产生了有价值的问答
   - 但这些内容完全进不到 mindvaults
```

### 2.3 解决什么

```
        ┌─ 智能路由 (#15) ──────────────────┐
        │  用户不用手动选 KB，系统自动挑       │
        │  日常 90% 问题质心匹配命中           │
        └─────────────────────────────────────┘
                        │
        ┌─ 概念网络 (#18) ──────────────────┐
        │  术语自动抽取、hover 解释            │
        │  RAG 上下文注入，LLM 更懂你的文档    │
        └─────────────────────────────────────┘
                        │
        ┌─ 知识沉淀 (#16 + #17) ────────────┐
        │  内部 QA + 外部对话 → 提炼 → 审核   │
        │  把 LLM 生成的价值回流到知识库       │
        └─────────────────────────────────────┘
                        │
        ┌─ 内容治理 (#19) ──────────────────┐
        │  重复检测、质量评分、过时标记        │
        │  知识库越用越干净，不是越用越乱       │
        └─────────────────────────────────────┘
```

### 2.4 对系统的帮助

| 维度 | 没有数据治理 | 有数据治理 |
|------|------------|-----------|
| **知识增长** | 仅靠上传文档（线性） | 文档 + QA 回流 + 外部对话（复利） |
| **检索质量** | 重复/低质内容抢占 top_k | 高质量 chunk 优先，superseded 排除 |
| **用户体验** | 手动选 KB，术语看不懂 | 自动路由，hover 看概念 |
| **跨平台** | 只在 mindvaults 里用 | Claude Code 等外部对话也能沉淀回来 |
| **长期维护** | 3 个月后知识库变成垃圾堆 | 持续治理，健康度可量化 |

| 检查点 | 状态 | 备注 |

### 2.7 未覆盖的边界

| 边界情况 | 影响 | 建议 |
|---------|------|------|
| **概念抽取 LLM 成本** | 每 chunk 一次 LLM 调用，大文档成本高 | 明确使用更便宜的模型，或批量处理（一次调 N 个 chunk） |
| **沉积库被用户删除** | 外部推送全部失败 | 系统保护（禁止删除 kb_type='deposition' 的 KB） |
| **质心更新失败** | KB 在自动模式下永远回退 Layer 2/3 | 重试 + 降级标记 + 监控告警 |
| **定时任务和用户请求争抢 DB 连接** | 提炼/扫描时影响问答性能 | 独立 worker 进程 + 只读从库（后期） |
| **insight 目标 KB 被删除后** | 已分配的 kb_chunks 成为孤岛 | 级联清理或保留在沉积库 |
| **多个 Skill 同时推送同一会话** | 重复数据 | 唯一索引兜底 (platform + session + question) |
