# 文档预处理服务 — 方案设计

> 状态：✅ 已实现 | 创建：2026-06-07 | 更新：2026-06-11 | 版本：v0.8.0 已落地 | 关联：[[18-知识库内容再组织]] [[05-数据库设计]]

## 背景

v0.7 引入了结构化预处理（`chunking_service.mode="structured"`），验证了「源头治理 > 事后清理」的核心判断。当前实现嵌入在 chunking_service 中，随着文件类型边界差异变大，需要独立为专门服务。

## 目标

将「原始文档 → 干净结构化文本」作为独立管道阶段，**每种文件类型有专门的预处理规则**，输出高质量、自包含的知识单元，显著减少后续治理负担。

## 处理管道

```
原始文件（pdf / md / txt / docx / doc）
    │
    ▼
┌─ Parser（P0-P1 不变，P2 增强）───────────────────────────┐
│  按文件类型提取文本，保留页码                              │
│  输出: [(text, page_number), ...]                        │
│  P2 DOCX 时增强为 ParsedPage(text, page, metadata)       │
│  pdf → PyPDF2/pdfplumber，逐页提取                        │
│  docx → python-docx，按段落提取（P2 保留样式元数据）      │
│  md/txt → 直接读取                                       │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─ Preprocessor（🆕 独立服务）──────────────────────────────┐
│  两阶段处理：跨页分析 → 逐页清洗                           │
│                                                          │
│  阶段一（跨页分析，仅 PDF 需要）：                          │
│    全文档扫描 → 识别页眉页脚重复行 → 返回剔除列表          │
│                                                          │
│  阶段二（逐页清洗，所有类型）：                              │
│    类型特化 clean()                                       │
│    PDF: ASCII 图表移除 → 标题识别 → 断行修复 → 页码剔除   │
│    MD:  代码块保护 → YAML frontmatter → 链接纯化          │
│    TXT: 噪声行过滤 → 空行归拢                              │
│    DOCX: 样式层级提取 → 列表/表格归一化（P2）             │
│                                                          │
│  阶段三（公共归拢，所有类型）：                              │
│    行分类 → 块归拢 → 标题+正文合并 → 碎片过滤              │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─ Chunker（不变）──────────────────────────────────────────┐
│  结构化段落 → 语义切片（RecursiveCharacterTextSplitter）   │

                     ▼

                  Embedder
```

## Parser ↔ Preprocessor 数据契约

### 关键设计决策

当前 Parser 输出 `[(text: str, page_number: int | None)]` 扁平文本，丢弃了样式/字体/坐标等结构信息。**分阶段处理**：

| 阶段 | 文件类型 | Parser 是否够用 | 说明 |
|------|---------|:---:|------|
| P0 | MD | ✅ | YAML frontmatter、代码块、Wiki 链接均基于纯文本 |
| P0 | TXT | ✅ | 编码检测需读原始 bytes（当前已按 utf-8 读，chardet 补一个 raw read） |
| P0 | PDF | ✅ | 页眉检测用跨页文本对比；标题识别用全大写/编号模式兜底 |
| P2 | DOCX | ❌ | 样式层级提取需要 `p.style.name`、表格需要 `doc.tables`，必须在 Parser 中保留 |

### P2 Parser 增强方案

```python
# P2 时引入结构化数据类
@dataclass
class ParsedPage:
    text: str
    page_number: int | None
    metadata: dict | None = None  # 可选的结构化元数据
    # DOCX 示例: {"lines": [{"text": "...", "style": "Heading 1", "bold": True}, ...],
    #             "tables": [[["cell1", "cell2"], ...]]}
    # PDF 示例:  {"font_sizes": [12, 14, ...], "char_positions": [(x, y), ...]}
```

P0-P1 阶段 Parser 保持不变，`ParsedPage` 仅 `text` + `page_number` 有值。P2 时增强 DOCX parser，同时保持向后兼容。

## 文件类型规则

### 1. Markdown（.md）

#### 核心设计：Section-based 切片

MD 文档天生有层级结构（`# → ## → ### → 段落 → 列表`），预处理器将文档解析为**节（Section）树**，以结构边界为切割点，字符数只作为上限约束。

**与旧版 `_structured_chunk` 的关键区别**：
- 旧版：归拢段落 → join 为文本流 → `RecursiveCharacterTextSplitter` 在 500 字符处一刀切（可能切断列表/表格/段落中部）
- 新版：解析 Section 树 → 每个 Section 独立输出 → 超长时沿子节/段落边界拆分 → 代码块/表格不拆分

**切片大小建议**（基于嵌入模型特性）：

| 范围 | 字符数 | 适用场景 | 结论 |
|------|:--:|------|------|
| 过短 | < 150 | 单句碎片 | LLM 无法独立理解 |
| 偏低 | 150-350 | 短段落 | 可接受，信息密度偏低 |
| **最佳** | **350-650** | **完整段落/小节** | 自包含知识单元，检索精度最高 |
| 偏高 | 650-850 | 长段落 | 可接受 |
| 过长 | > 850 | 多段落拼合 | 语义稀释 |

**目标值 500 字符，弹性范围 350-650（±30%）**。与当前 `kb_config.chunk_size=500` 默认值一致。

#### 清洗规则

| 步骤 | 规则 | 说明 |
|------|------|------|
| ① YAML frontmatter | 提取 title/tags/description 为元数据，正文不包含 `---` 块 | Obsidian vault 导入常见 |
| ② 代码块保护 | ` ``` ` 围栏内容标记为不可拆分，原样保留 | 即使超长也不拆分 |
| ③ 图片链接纯化 | `![alt](url)` → `[图片: alt]` | 避免 URL 碎片 |
| ④ Wiki 链接 | `[[page]]` → `page`，`[[page\|alias]]` → `alias` | Obsidian 兼容 |
| ⑤ HTML 标签 | 移除 `<div>` `<span>` 等，保留 innerText | MD 中混入 HTML |
| ⑥ 表格保留 | 表格标记为不可拆分单元 | 结构完整性 |
| ⑦ 列表成组 | 连续 `- ` / `* ` / 数字列表 → 保持在一起 | 不会在列表中间切断 |

#### Section 数据结构

```python
@dataclass
class Section:
    heading: str          # "## Python GIL 限制及解决方案"
    level: int            # 2 (## = level 2), 0 表示无标题正文段
    content: str          # 标题下的直接正文（不包含子标题内容）
    subsections: list[Section]  # 子级 Section（### = level 3 等）
    total_length: int     # heading + content + 所有子节的总字符数
    unsplittable: bool    # True = 代码块 / 表格，完整保留不拆分
```

#### Section 树解析

```python
def _parse_sections(self, body: str) -> list[Section]:
    """将 MD 正文解析为 Section 树。

    1. 按 # 标题行切分，构建标题层级栈
    2. 每遇到一个标题，向上找到合适的父级 Section
    3. 标题之间的内容归入该 Section.content
    4. 代码块/表格标记 unsplittable=True
    """
```

**有标题文档**（最常见的 Obsidian vault 场景）：

```
## Django ORM 性能优化              ← Section(level=2)
  ├── ### select_related 详解       ← Section(level=3), 是 level=2 的 subsections
  │     ├── (段落 text)             ← 归入 level=3 的 content
  │     └── (段落 text)
  ├── ### prefetch_related 详解     ← Section(level=3)
  └── (无标题结语)                  ← 归入 level=2 的 content
```

**无标题文档**：用隐式结构层级替代：

| 隐式层级 | 触发条件 | 对应显式标题 | 说明 |
|----------|---------|:---:|------|
| Level 1 分隔 | 连续 ≥ 2 个空行（`\n\n\n`） | `##` | 大节边界 |
| Level 2 分隔 | 单个空行（`\n\n`） | `###` | 小节/段落组边界 |
| Level 3 单元 | 列表组首尾、代码块首尾 | `####` | 不可拆分单元 |

```
Python 是一门广泛使用的编程语言。       ┐
它的设计哲学强调代码可读性。             │ Level 2: 段落组 A (200 chars)
                                       ┘
                                       ← Level 1: 双空行分隔
常用的 Python Web 框架：                ┐
- Django：全栈框架                      │ Level 2: 列表组 (300 chars)
- Flask：微框架                        │
- FastAPI：现代异步框架                  ┘
```

#### Section → Chunk 映射算法

```python
def _sections_to_chunks(
    self, sections: list[Section], target: int = 500
) -> list[str]:
    """将 Section 树映射为 chunk 列表。

    弹性规则（target=500，弹性 ±30% = 350-650）：
    - Section 350-650 chars → 完整保留
    - Section < 350 chars    → 尝试与下一相邻 Section 合并
      → 合并后 ≤ 650 → 合并
      → 合并后 > 650 → 各自独立
    - Section > 650 chars    → 沿子节边界拆分
      → 子节 ≤ 650 → 子节作为独立 chunk
      → 子节 > 650 → 沿段落边界（\\n\\n）拆分
        → 单段 > 650 → 沿句子边界拆分（最后手段）
    - unsplittable=True      → 无论长度，完整保留

    返回 chunk 文本列表。
    """
```

**示例**（target=500）：

```
输入 Section 树 (Django ORM 优化, total=2500 chars):
  ## Django ORM 性能优化 (level=2)
    ├── ### select_related 详解 (level=3, 800 chars)
    │     ├── 基础用法 (300 chars)
    │     └── 注意事项 (500 chars)
    ├── ### prefetch_related 详解 (level=3, 700 chars)
    │     └── [代码块] (400 chars, unsplittable=True)
    ├── ### 性能对比 (level=3, 600 chars)
    │     ├── 文字说明 (200 chars)
    │     └── [表格] (400 chars, unsplittable=True)
    └── 其他文本 (400 chars)

输出 chunk（7 个自包含单元）:
  chunk_1: "## Django ORM 性能优化"           ← level=2 title 独立
  chunk_2: "### select_related 详解\n基础用法"  ← 300 (独立)
  chunk_3: "### select_related 详解\n注意事项"  ← 500 (在理想区间)
  chunk_4: "### prefetch_related\n[代码块]"     ← 700? 不——代码块 400 unsplittable，完整保留
  chunk_5: "### 性能对比\n文字说明"              ← 200 < 350，尝试合并
                                              → 与表格合并 = 600 > 650? 不，正好 600
                                              → 但表格 unsplittable → 不合并，各自独立
  chunk_5: "### 性能对比\n文字说明"              ← 200 (独立，短但自包含)
  chunk_6: "### 性能对比\n[表格]"               ← 400 (unsplittable，完整保留)
  chunk_7: "其他文本"                           ← 400 (在理想区间)
```

#### 与 Chunker 的协作

预处理器输出**以 Section 为单位的独立文本**，chunker 对每个 Section 单独调用 `_semantic_chunk`：

```python
# ingestion_service.py 调用链
pages = await parse_document(file_path, "md")         # [(full_text, None)]
pages = await preprocessor.preprocess("md", pages)    # [(section_1, None), (section_2, None), ...]
chunks = await chunk_pages(pages, mode="semantic")    # 每个 section 独立做 semantic chunk
```

因为 Section 长度已控制在 350-650 弹性区间，`_semantic_chunk` 对单个 Section 大概率原样输出。仅当 Section > 650（未能在 Section 树阶段拆分的超长段落）时，semantic splitter 才介入，且此时切割大概率落在段落边界（因为 Section 内已是单一段落）。

### 2. PDF（.pdf）

#### 阶段一：跨页分析

| 步骤 | 规则 | 说明 |
|------|------|------|
| ① 页眉页脚检测 | 在所有页面中 ≥3 页出现的相同行（归一化后）→ 标记剔除 | 先全扫描再清洗，O(n) 用哈希计数 |
| ② 水印关键词 | 匹配 "Confidential" "Draft" "内部" 等跨页关键词 | |

#### 阶段二：逐页清洗

| 步骤 | 规则 | 说明 |
|------|------|------|
| ③ ASCII 图表 | box-drawing 字符行及包围行整体移除 | `┌─┐ │X│ └─┘` |
| ④ 换行修复 | 单行 < 40 字符且下一行首字母小写 → 合并 | PDF 断行问题 |
| ⑤ 空行归拢 | 连续 ≥3 空行 → 压缩为 1 行 | |
| ⑥ 页码/水印 | 匹配 `^\s*\d+\s*$` 的孤立数字行 + 阶段一标记的行 | |
| ⑦ 标题识别 | 全大写模式 `^[A-Z][A-Z\s]{10,}` 或编号模式 `^\d+[\.\s]\s+\S` | 无字体信息时的启发式 |

### 3. Word（.docx / .doc）

| 步骤 | 规则 | 说明 |
|------|------|------|
| ① 样式提取 | Heading 1-6 → `#` 标题标记，粗体+大字号 → 标题候选 | **依赖 P2 Parser 增强** |
| ② 表格处理 | 表头+行 → markdown 表格格式 | 保留结构信息 |
| ③ 列表归一化 | 有序/无序列表 → `- ` 前缀 | |
| ④ 文本框/页眉页脚 | 跳过（这些通常是装饰性内容） | |
| ⑤ 结构归拢 | 标题+正文合并 | 公共规则 |

### 4. 纯文本（.txt）

| 步骤 | 规则 | 说明 |
|------|------|------|
| ① 编码检测 | chardet 读原始 bytes 检测编码 → UTF-8，记录检测置信度 | 避免乱码，注意 chardet 是同步 CPU 操作 |
| ② 噪声行过滤 | 纯数字/标点行、超短行（< 3 字符）、连续重复行 | |
| ③ 空行归拢 | 连续空行 → 1 行 | |
| ④ 邮件/日志头 | `From:` `To:` `Date:` 等 → 保留但归一化 | 对话记录场景 |
| ⑤ 基本归拢 | 短段落合并 | 公共规则 |

### 5. 公共归拢规则（PDF / TXT / DOCX 最终执行）

> **MD 类型不执行此规则**。MD 使用 Section 树解析 + Section→Chunk 映射，替代 block merge 流程。
> PDF / TXT / DOCX 沿用 `_classify_line → _build_blocks → _merge_blocks` 管道（迁移自 chunking_service），因为它们没有 `#` 标题层级。

| 规则 | 说明 |
|------|------|
| 标题识别 | `#` 标题（PAIDF/DOCX 由前一步启发式生成）|
| 标题+正文合并 | 标题与其紧跟的正文段落合并为一个知识单元 |
| 短段落合并 | 相邻短段落（< 120 字符）合并 |
| 列表成组 | 连续列表项保持在一起 |
| 代码块完整 | 围栏代码块不拆分 |
| 质量兜底 | 最终再过 `filter_chunks`（< 50 字符、box 残留） |

## 架构设计

### 文件结构

```
backend/app/services/
  preprocessor/
    __init__.py           # PreprocessorRouter: 按文件类型分发
    base.py               # BasePreprocessor + 公共归拢规则（迁移自 chunking_service）
    markdown.py           # MarkdownPreprocessor
    pdf.py                # PDFPreprocessor（含两阶段处理）
    docx.py               # DocxPreprocessor（P2）
    txt.py                # TxtPreprocessor
```

### 核心类设计

```python
# ── PreprocessorRouter ──────────────────────────────────────

class PreprocessorRouter:
    """按文件类型路由到对应预处理器。"""

    _processors: dict[str, BasePreprocessor] = {
        "md": MarkdownPreprocessor(),
        "pdf": PDFPreprocessor(),
        "docx": DocxPreprocessor(),
        "doc": DocxPreprocessor(),
        "txt": TxtPreprocessor(),
    }

    async def preprocess(
        self, doc_type: str, pages: list[tuple[str, int | None]]
    ) -> list[tuple[str, int | None]]:
        """预处理入口：跨页分析 → 逐页清洗 → 公共归拢。"""
        processor = self._processors.get(doc_type)
        if processor is None:
            return pages  # 未知类型，原样返回
        return await processor.process(pages)


# ── BasePreprocessor ────────────────────────────────────────

class BasePreprocessor:
    """预处理器基类。

    默认三阶段模板方法（PDF/TXT/DOCX 使用）：
      阶段一: cross_page_analyze(pages) → 跨页分析（默认空操作）
      阶段二: clean(text, page_num, analysis_result) → 类型特化清洗
      阶段三: merge(pages) → 公共归拢（_classify_line / _build_blocks / _merge_blocks）

    MarkdownPreprocessor 重写 process() 整体逻辑：
      Section 树解析 → 行内清洗 → Section→Chunk 弹性映射
    """

    async def process(
        self, pages: list[tuple[str, int | None]]
    ) -> list[tuple[str, int | None]]:
        """默认三阶段管道。MD 等类型可重写此方法。"""
        # 阶段一：跨页分析（只有 PDF 重写此方法）
        analysis = await self.cross_page_analyze(pages)

        # 阶段二：逐页清洗
        cleaned: list[tuple[str, int | None]] = []
        for text, page_num in pages:
            text = await self.clean(text, page_num, analysis)
            cleaned.append((text, page_num))

        # 阶段三：公共归拢
        return await self.merge(cleaned)

    async def cross_page_analyze(
        self, pages: list[tuple[str, int | None]]
    ) -> dict | None:
        """跨页分析，子类按需重写。返回分析结果传给 clean()。"""
        return None

    async def clean(
        self, text: str, page_num: int | None, analysis: dict | None
    ) -> str:
        """类型特化清洗，子类重写。"""
        return text

    async def merge(
        self, pages: list[tuple[str, int | None]]
    ) -> list[tuple[str, int | None]]:
        """公共归拢：行分类 → 块构建 → 标题合并 → 碎片过滤。"""
        # 迁移自 chunking_service 的 _classify_line / _build_blocks / _merge_blocks
        ...


# ── MarkdownPreprocessor ──────────────────────────────────

class MarkdownPreprocessor(BasePreprocessor):
    """MD 预处理器：Section 树解析 + 弹性映射。

    重写 process() 整体逻辑，不使用默认的逐页清洗+公共归拢管道。
    """

    async def process(
        self, pages: list[tuple[str, int | None]]
    ) -> list[tuple[str, int | None]]:
        """MD Section-based 处理管道。"""
        text = pages[0][0]  # MD 只有一页

        # 1. YAML frontmatter
        metadata, body = self._extract_frontmatter(text)

        # 2. 行内清洗（不改结构）
        body = self._clean_inline(body)

        # 3. 结构解析 → Section 树
        sections = self._parse_sections(body)

        # 4. Section → Chunk 映射（350-650 弹性）
        chunks = self._sections_to_chunks(sections, target=500)

        return [(c, None) for c in chunks]

    # ── 内部方法 ──

    def _extract_frontmatter(self, text: str) -> tuple[dict, str]:
        """提取 YAML frontmatter，返回 (metadata, body)。"""
        ...

    def _clean_inline(self, text: str) -> str:
        """行内清洗：Wiki 链接、图片链接、HTML 标签。"""
        ...

    def _parse_sections(self, body: str) -> list[Section]:
        """按 # 标题层级构建 Section 树。无标题时用隐式结构。"""
        ...

    def _sections_to_chunks(
        self, sections: list[Section], target: int = 500
    ) -> list[str]:
        """弹性映射算法：< 350 合并、350-650 保留、> 650 子节拆分。"""
        ...
```

| `_merge_blocks(blocks)` | `preprocessor/base.py` — 公共方法 | 同上 |
| `_SHORT_THRESHOLD = 120` | `preprocessor/base.py` — 常量 | 同上，最终可配置化 |
| `_merge_report()` | `preprocessor/base.py` — 公共方法 | 同上 |
| `_structured_chunk()` | 简化为语义 pass-through | **所有文件类型**的预处理均移到 preprocessor，chunker 不再做结构化处理 |
| `chunk_pages()` | 不变，`mode="semantic"` | 因为预处理已在 ingestion 阶段完成 |
| — | `preprocessor/markdown.py` — 新增 | **Section 树解析 + 弹性映射**，重写 process()，不使用 base 的 merge 管道 |

| 现有 | 改动 |

## 重索引机制

预处理规则迭代后（bug 修复或规则改进），已入库文档需要重新走预处理+切片。

### 方案

复用 `ingestion_service.schedule_ingestion()` 的现有流程。新增 API：

```
POST /api/v1/kb/documents/{doc_id}/reindex
  → 标记文档状态为 PROCESSING
  → schedule_ingestion(doc_id, ...)
  → 预处理规则已更新，全链路重新执行
```

### 注意事项

- 重索引时旧 chunk 先物理删除（通过 `db.delete(KbChunk)` + commit），再重新生成
- 如果 chunk 有 `supersedes` / `kb_chunk_links` 关联，一并清理
- 重索引后 KB 质心向量需要重新计算

> 此端点可在现有 `documents.py` 路由中增加，不在本次计划的独立改动清单中。

## 性能考量

| 关注点 | 分析 | 应对 |
|--------|------|------|
| PDF 页眉检测 O(n²) 风险 | 对 100 页文档逐对对比所有行，最大 ~10000 次比较，仍在毫秒级 | 使用 `Counter` 哈希计数降为 O(n)，重复 ≥3 次即标记 |
| chardet 编码检测 | 同步 CPU 操作，阻塞事件循环 | Semaphore(3) 已限制并发摄入数；chardet 检测 < 10ms for < 1MB |
| async 的实际收益 | 所有 clean 操作都是 CPU 密集（正则、字符串），async 不带来并行收益 | 保持 async 签名与管道一致（ingestion 整个链路是 async），内部不强行做 CPU 并行 |
| 大文档内存 | 全文档页面列表同时加载在内存中 | 已有限制：PDF > 500 页的文档极少；如需优化可分批处理 |
| 公共归拢的复杂度 | 逐行分类 + 块构建 + 合并 三步均为 O(n) | 当前已运行稳定，迁移不增加复杂度 |

## 验收标准

- [ ] Markdown：YAML frontmatter 提取正确，代码块完整不拆分，Wiki 链接 `[[page\|alias]]` → `alias`

- [ ] 摄入管道：parser → preprocessor → chunker(semantic) → filter → embedder 全链路通
- [ ] 配置开关：`preprocess_enabled=false` 时回退到旧行为

- [ ] 预处理后 `< 50` 字符的 chunk 占比 < 5%（从当前基线下降）
