# 多知识库场景下的智能路由：从向量匹配到三层降级

> mindvaults 是一个本地私有化的 RAG 知识库，支持用户创建多个知识库。本文记录 KB 智能路由的技术方案——如何在用户不手动选择的情况下，自动判断该检索哪个知识库。


## 一、问题

当前系统支持多 KB，但对话时固定走 `session.kb_id` 或默认 `id=1`。用户问"GIL 锁怎么解决"，系统不会自动判断该去 Python 文档库检索——除非用户先手动切库。

```
# 当前逻辑（chat_service.py）
kb_id = req.kb_id if req.kb_id is not None else (session.kb_id if session else 1)
```

另外，聊天框标注"关联 N 个本地知识库"会误导用户以为已经在跨库检索。

核心矛盾：**用户不知道答案在哪个库，但系统有足够信息去判断，只是没做。**


## 二、方案选型

### 2.1 为什么不用 KB 描述做匹配

直觉方案：把用户问题和每个 KB 的 name + description 做语义匹配。

但 KB 描述是**分类标签**（"存放 Python 技术文档"），用户问题是**具体内容**（"GIL 锁怎么解决"）。这两类文本在不同语义空间，余弦相似度不可靠。实测中，几乎任何技术问题对所有 KB 的描述文本相似度都在 0.3-0.5 之间，区分度极低。

### 2.2 质心向量匹配

我们不匹配元数据，匹配内容本身。

每个 KB 下的所有 chunk 都已经被 embed 成 1024 维向量。取这些向量的均值，就是这个 KB 的质心向量（centroid embedding）——数学上代表了该 KB 的内容中心。

用户问题的向量和每个 KB 的质心向量做余弦距离：

```sql
SELECT kb_id, centroid_embedding <=> :question_vec AS distance
FROM kb_knowledge_bases
WHERE centroid_embedding IS NOT NULL
  AND kb_type != 'deposition'  -- 排除系统内部沉淀库
ORDER BY distance
LIMIT 1;
```

一次 pgvector 查询，< 1ms。质心和问题在同一个语义空间，匹配准确率预估 80-90%。

### 2.3 质心维护策略

| 操作 | 策略 | 复杂度 |
|------|------|--------|
| 新增 chunk | 增量更新 `(old × N + new) / (N + 1)` | O(1) |
| 删除 chunk | 随机采样 1000 个 chunk 重算 | O(1000)，~10ms |
| 冷 KB（无 chunk） | 质心设为 NULL，Layer 1 自动跳过 | — |

不依赖后台任务队列。增量更新 < 1ms，采样重算 ~10ms，都在请求同步流程内完成。

### 2.4 但质心不够时怎么办

两个 KB 内容重叠（如"Python 技术文档"和"数据分析"都有 Python 内容），质心距离可能很接近。这时候只选第一名的风险太高。

**gap 规则**：第一名和第二名的距离差 < 阈值（默认 0.08），不猜，降级给 LLM 做语义判断。

```python
if second and (second[1] - first[1]) < gap_threshold:
    return None  # 前两名太接近 → 降级 Layer 2
```


## 三、三层降级架构

```
用户提问
    │
    ▼
Layer 1: 质心向量匹配（< 1ms，零 LLM 成本）
    │  查询 kb_knowledge_bases 的 centroid_embedding 列
    │  条件：distance ≤ 0.40 且 gap > 0.08
    │
    ├── 命中 → 直接检索该 KB
    └── 未命中 ↓

Layer 2: LLM 语义路由（~200-500ms，一次非流式调用）
    │  和问答同一套 provider/model，temperature=0
    │  输入：用户问题 + 各 KB 的 name + description + 概念标签（来自概念抽取模块）
    │  输出：{"kb_id": int, "confidence": float}
    │  条件：confidence ≥ 0.60
    │
    ├── 命中 → 检索该 KB
    └── 未命中 ↓

Layer 3: 用户引导
    │  前端展示："我不确定该用哪个知识库。你可以："
    │  选项：指定 KB / 全库搜索 / 换个方式描述
    └── 用户选择 → 走对应路径
```

**阈值全部可配**，存在 `system_config` 中：

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `route_centroid_threshold` | 0.40 | Layer 1 距离阈值 |
| `route_centroid_gap` | 0.08 | 前两名最小差距 |
| `route_llm_confidence` | 0.60 | Layer 2 置信度阈值 |


## 四、异常兜底：不画"正常流程"，画"所有可能出错的地方"

设计阶段我们没有只画 happy path，而是把所有异常场景穷举出来，逐一给兜底方案：


### Layer 1 防护

```python
async def match_kb_by_centroid(db, question_embedding, threshold, gap):
    # 排除沉积库、排除无质心的 KB
    rows = await db.execute(
        select(KbKnowledgeBase)
        .where(
            KbKnowledgeBase.centroid_embedding.is_not(None),
            KbKnowledgeBase.kb_type != "deposition",
        )
    )
    kbs = rows.all()
    
    if not kbs:
        return None  # 无候选 → 降级 Layer 2
    
    results = sorted(
        [(kb, cosine_distance(kb.centroid_embedding, question_embedding)) 
         for kb in kbs],
        key=lambda x: x[1]
    )
    
    first, second = results[0], results[1] if len(results) > 1 else (None, None)
    
    if first[1] > threshold:
        return None  # 第一名也太远
    if second and (second[1] - first[1]) < gap:
        return None  # 前两名太接近 → LLM 判断
    
    return {"kb_id": first[0].id, "kb_name": first[0].name, 
            "distance": round(first[1], 4), "method": "centroid"}
```

### Layer 2 防护

```python
async def route_kb_by_llm(db, question, kbs):
    try:
        response = await llm_call_non_stream(
            system="你是知识库路由助手...",
            user_prompt=build_route_prompt(question, kbs),
            temperature=0,
        )
        result = parse_json(response)
        
        # 校验 LLM 返回的 kb_id 是否真实存在（防幻觉）
        kb = await db.get(KnowledgeBase, result["kb_id"])
        if kb is None or kb.kb_type == "deposition":
            return None
        
        if result["confidence"] < route_llm_confidence:
            return None  # 低置信度
        
        return {"kb_id": kb.id, "kb_name": kb.name,
                "confidence": result["confidence"], "method": "llm_route"}
    except Exception:
        logger.error(f"llm_route_failed question_len={len(question)}")
        return None  # 任何异常 → 降级 Layer 3
```

### 全量场景覆盖

| # | 场景 | 兜底 |
|---|------|------|
| 1 | 所有 KB 无文档 | 前置检测 → 引导上传，不走路由 |
| 2 | Layer 1 前两名距离接近 | gap 规则 → 降级 Layer 2 |
| 3 | 问题太模糊 | 逐层降级 → Layer 3 引导 |
| 4 | 问题与所有 KB 不相关 | LLM 判断全部不相关 → Layer 3 |
| 5 | LLM 路由调用失败 | try/catch → 用 Layer 1 最优结果或 Layer 3 |
| 6 | LLM 返回不存在 kb_id | db.get 校验 → 降级 Layer 3 |
| 7 | 质心计算出错 | 异常捕获 → 保持旧值 + 日志告警 |
| 8 | KB 删除后路由引用 | 检索前 db.get 再次验证 |
| 9 | 前端状态和后端不一致 | 后端以收到的 kb_id 参数为准 |


## 五、前端交互

原来的 `<select>` 下拉框替换为浮动面板。LLM 回答生成时不可切换，新建会话默认回到"自动"。

匹配结果通过已有的 SSE thinking 流输出，不新增 UI：

```json
{"phase":"routing","message":"质心匹配: Python 技术文档 (距离 0.23)","kb_id":2,"method":"centroid"}
{"phase":"routing","message":"LLM 路由: 运维手册 (置信度 0.85)","kb_id":3,"method":"llm_route"}
{"phase":"routing","message":"未能确定匹配知识库，请手动选择","method":"fallback"}
```

用户交互规则：

| 选择 | kb_id | 后端行为 |
|------|-------|---------|
| 自动 | null | 三层路由 |
| 指定 KB | N | 直接检索该 KB |
| 全库搜索 | 0 | 跨所有 KB 检索 |


## 六、数据库改动

```sql
-- kb_knowledge_bases 新增加列
ALTER TABLE kb_knowledge_bases
  ADD COLUMN centroid_embedding vector(1024),
  ADD COLUMN centroid_updated_at TIMESTAMPTZ;

-- system_config 新增路由阈值
ALTER TABLE system_config
  ADD COLUMN route_centroid_threshold FLOAT NOT NULL DEFAULT 0.40,
  ADD COLUMN route_centroid_gap FLOAT NOT NULL DEFAULT 0.08,
  ADD COLUMN route_llm_confidence FLOAT NOT NULL DEFAULT 0.60;
```


## 七、监控埋点

路由事件全部写入 `kb_monitor_events` 表：

| event | status | 触发条件 |
|-------|--------|---------|
| `centroid_hit` | success | Layer 1 命中 |
| `centroid_gap` | warning | 前两名接近，降级 |
| `llm_route_hit` | success | Layer 2 命中 |
| `llm_route_failed` | failed | LLM 调用失败 |
| `llm_route_invalid_kb_id` | failed | LLM 返回无效 kb_id |
| `route_fallback` | warning | 进入 Layer 3 |

告警规则：LLM 路由连续失败 3 次触发告警，Layer 3 降级率超过 20% 触发告警，质心计算失败立即告警。
