# 知识库的"复利效应"：从单向检索到对话知识回流

> mindvaults 的知识库之前只进不出——上传文档、切片、检索、回答、结束。LLM 结合多份文档产生的优质回答，用一次就丢了。知识沉淀模块让对话中产生的价值回流到知识库，下一次提问直接命中已解答过的知识。


## 一、问题

当前 QA 流程是单向管道：

```
用户提问 → 检索 chunk → LLM 生成 → 存入 kb_qa_records → 结束
```

`kb_qa_records` 表从创建之日起就是只写不读。LLM 结合 3-5 份参考文档生成的回答，质量往往超过任何单一文档片段，但这些优质回答从未被反向利用。

三个痛点：

1. **知识只进不出**：文档上传 → 检索 → 回答 → 丢弃。LLM 生成的有价值内容没有回流。
2. **没有反馈环路**：kb_qa_records 只有写入，从未被回读利用。知识库是单向的。
3. **外部对话无法回流**：用户在 Claude Code 里产生的有价值问答，完全进不到系统。


## 二、方案选型

### 2.1 存原文还是提炼

直觉方案：把整段 QA 原文存成 chunk。

但 QA 原文有很多噪音（"你好""请继续""帮我总结一下"），直接入库会污染检索结果。我们选择 **LLM 二次提炼**：从 QA 对话中提取独立、自包含的知识点，脱离原始对话也能读懂。

### 2.2 即时还是定时

每次对话结束立刻提炼？不合适：
- 阻塞问答流程（提炼需要一次额外的 LLM 调用）
- 短答案不值得提炼（"你好""谢谢"→ 跳过）
- 后续去重需要跨多条 QA 判断

选择**定时批处理**：默认每日凌晨 2:00，汇总过去 24 小时的 QA 记录，批量调 LLM 提炼。不阻塞正常问答。

### 2.3 去重策略

两层去重：

- **ID 去重**：同一 `source_qa_id` 已提炼过 → 跳过。零成本。
- **向量去重**：新知识点 embedding 和已有 approved insight 做余弦相似度，> 0.92 → 跳过。

### 2.4 知识归集到哪

所有 insight 统一归集到系统知识库（id=1，"默认系统库"），通过 `target_kb_id` 记录应该分配到哪个业务 KB。审核通过后，insight 落地为 `kb_chunk` 写到目标 KB 的"💡 知识沉淀"虚拟文档下。

用户对话时走智能路由回答了 Python 的问题，系统知道 session 属于哪个 KB，自动预填 `target_kb_id`。审核时用户可以改目标 KB。


## 三、数据流

```
对话提问 ──→ 智能路由 ──→ KB-X 回答 ──→ kb_qa_records
                                              │
                                    定时批处理（凌晨 2:00）
                                              │
                                              ▼
                                    LLM 提炼知识点（非流式，temperature=0）
                                              │
                                    ID 去重 + 向量去重（阈值 0.92）
                                              │
                                              ▼
                                    kb_insights（系统库，status=pending）
                                         │
                                    ┌─────┴─────┐
                                    │  用户审核   │
                                    │  ✓ 通过    │  ✗ 拒绝   │  🗑 删除
                                    └─────┬─────┘
                                          │ 通过
                                          ▼
                                    kb_chunks（目标 KB 的 💡 知识沉淀 文档）
                                    source_type='insight'
                                    ↓
                              参与 RAG 联合检索
```


## 四、检索集成

已通过的 insight 落地为 `kb_chunk`，和普通文档切片在同一语义空间。检索时不需要特殊处理——直接命中。

同时在 `kb_insights` 表保留原记录，带 `source_qa_ids` 追溯原始对话，用户可以从知识点跳回去看完整上下文。

引用展示区分来源：
- `📄 文档: xxx.md` — 原始文档切片
- `💡 知识沉淀: CPython GIL 限制及解决方案` — 对话提炼


## 五、数据库设计

```sql
CREATE TABLE kb_insights (
    id              BIGSERIAL PRIMARY KEY,
    kb_id           BIGINT NOT NULL,        -- 统一归集到系统库
    target_kb_id    BIGINT,                 -- 审核通过后分配到哪个业务 KB

    title           VARCHAR(255) NOT NULL,   -- LLM 提炼的标题
    content         TEXT NOT NULL,           -- 知识点正文（自包含）
    embedding       vector(1024),           -- 向量，用于去重

    source_qa_ids   BIGINT[] NOT NULL,      -- 来源 QA 记录 ID
    source_doc_ids  BIGINT[],               -- 引用文档 ID

    status          VARCHAR(20) DEFAULT 'pending',  -- pending/approved/rejected
    reviewed_at     TIMESTAMPTZ,
    confidence      FLOAT DEFAULT 0.0,      -- LLM 自评置信度
    tags            VARCHAR(50)[],          -- 自动标签

    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

-- HNSW 向量索引，用于去重
CREATE INDEX idx_insights_embedding_hnsw ON kb_insights
    USING hnsw (embedding vector_cosine_ops);
```

配置项存在 `system_config` 中：

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `insight_extraction_enabled` | true | 启用开关 |
| `insight_extraction_schedule` | "02:00" | 批处理触发时间 |
| `insight_min_answer_length` | 200 | 最短答案字符数 |
| `insight_dedup_threshold` | 0.92 | 向量去重阈值 |
| `insight_auto_approve_confidence` | 0.95 | 自动通过置信度 |


## 六、LLM 提炼 Prompt

```
System: 你是一个知识提炼助手。请从以下对话中提取独立、自包含的知识点，
以 JSON 数组返回。要求：
1. 每个知识点有独立标题，脱离对话也能读懂
2. 保留所有关键信息，不丢失细节
3. 如果对话太浅或信息量不足，跳过不提炼（返回空数组）
4. 标注每个知识点的置信度（0-1）
5. 为每个知识点打 1-5 个标签

返回格式（严格 JSON）：
[{"title":"...","content":"...","confidence":0.9,"tags":["..."]}]
```

`temperature=0`，非流式，批量处理。置信度 ≥ 0.95 自动通过审核，< 0.95 进入待审核队列。


## 七、前端

审核中心在数据治理页面（`/kb/manage`），三个标签：

- **待审核**：卡片展示标题、正文（可展开）、置信度进度条、标签、来源对话。操作：通过/拒绝/删除，通过时选择目标 KB。
- **已通过**：展示已入库的知识点，可删除。
- **已拒绝**：展示被拒绝的知识点，可删除。

对话页每条助手消息底部有「💾 保存到知识库」按钮，手动触发单条提炼。


## 八、监控埋点

| event | 触发条件 |
|-------|---------|
| `insight_batch_started` | 定时批处理开始 |
| `insight_batch_completed` | 批处理完成，记录提炼/跳过/去重数 |
| `insight_batch_failed` | 批处理失败 |
| `insight_approved` | 审核通过 |
| `insight_rejected` | 审核拒绝 |
| `insight_to_chunk` | 知识点落地为 kb_chunk |
