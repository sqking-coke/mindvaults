# 知识库术语关联：从 LLM 抽取到 RAG 上下文注入

> mindvaults 是一个本地私有化的 RAG 知识库。本文记录概念术语关联的技术方案——如何从文档中自动抽取领域概念，在对话时自动注入 LLM 上下文，让 AI 真正理解你的知识库在讲什么。


## 一、问题

RAG 的标准流程：用户提问 → 向量检索 → Top-K chunk 拼进 Prompt → LLM 生成回答。

这个流程有一个盲区：**检索到的 chunk 用到了领域术语，但 LLM 不知道这些术语的定义。**

举个例子。你上传了一份《KB 智能路由方案》文档，里面定义了"质心向量匹配""gap 规则""三层降级"等概念。用户问"质心向量匹配失败了怎么办？"——系统检索到了相关 chunk，但 chunk 里只是**使用**这些术语，不会在每个片段里重新定义一遍。

LLM 看到陌生的领域术语，结果无非三种：

| # | 行为 | 后果 |
|---|------|------|
| 1 | 大胆猜测含义 | 答非所问 |
| 2 | 承认不知道 | 用户失望 |
| 3 | 从上下文勉强推断 | 似是而非 |

核心矛盾：**知识库文档里有术语定义，LLM 也检索到了相关片段，但定义本身没有被有效传递。**


## 二、方案选型

### 2.1 方案 A：让 LLM 读全文自己归纳

直接把整篇文档塞进 System Prompt，让 LLM 边读边理解术语。

**否决理由**：上下文窗口有限，多文档场景下更不可行。而且 LLM 归纳出的术语定义和原文可能不一致——RAG 的立命之本就是忠于知识库，我们不能在术语层面引入幻觉。

### 2.2 方案 B：静态术语表

用户手动维护一份 CSV，列出术语和定义，上传后系统按关键词匹配注入。

**否决理由**：维护成本高。用户上传新文档后不会记得去更新术语表。知识库的价值之一就是自动化，术语管理不应是额外负担。

### 2.3 方案 C：自动抽取 + 语义去重 + 上下文注入（选用）

| 阶段 | 做什么 | 触发时机 |
|------|--------|---------|
| 抽取 | LLM 从 chunk 中提取领域概念，生成 ≤500 字定义 + ≤100 字摘要 | 文档摄入时，每个 chunk 处理完立即执行 |
| 去重 | 精确去重（同 KB 下 LOWER(name) 唯一）+ 语义去重（pgvector cosine 相似度 > 0.85） | 抽取时同步执行 |
| 注入 | RAG 检索完成后，查出检索到的 chunk 关联的概念，摘要拼入 System Prompt | 每次问答的上下文构建阶段 |
| 展示 | 前端 hover 卡片在回答中高亮术语，鼠标悬停显示摘要 | SSE 流式输出完成后 |

每个环节都不需要用户干预，概念库随文档增长自动演进。

```

    │

    │
    ▼

    │
    ▼

```


## 四、LLM 抽取：不只是一个 Prompt

### 4.1 System Prompt 设计

抽取质量取决于 Prompt 的边界感。不给边界，LLM 会把"API 参数名""数据表名""配置项名"全抽出来。

我们的 Prompt 明确了**排除标准**：

```
只提取值得在领域课程中教学的概念（"如果你要教别人理解这个领域，必须解释哪些概念？"）
不要提取：API 参数名、数据表名、配置项名、普通名词、显而易见的功能描述
提取标准：这个概念的出现，对理解整个文档有实质帮助
```

以及**合并标准**：

```
同一概念的多种称呼（全称/简称/英文）合并为 aliases，不要单独列一条
如果两个概念的定义高度重叠，合并为一个
```

配置：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| temperature | 0 | 抽取不需要创意 |
| max_per_round | 5 | 每 chunk 最多抽取 5 个概念，宁缺毋滥 |
| min_chunk_length | 500 | 短于 500 字符的 chunk 跳过 |
| confidence 阈值 | — | LLM 对每个概念输出 0-1 信心分，定义模糊/边界不清的自动 ≤0.7 |

### 4.2 JSON 解析容错

LLM 返回不定形。我们做了三层容错：

```python
def _parse_extraction_response(raw: str) -> list[dict]:
    # Layer 1: 直接解析 JSON
    try: return json.loads(raw)
    except: pass

    # Layer 2: 提取 ```json ... ``` 代码块
    match = re.search(r"```(?:json)?\s*([\s\S]*?)\s*```", raw)

    # Layer 3: 找到第一个 [ ... ] 数组
    match = re.search(r"\[[\s\S]*\]", raw)

    # 全部失败 → 记录日志，返回 []
    logger.warning(f"concept_extraction_parse_failed ...")
    return []
```

结构化的 LLM 输出（JSON Schema / tool_use）可以根治这个问题，后续版本会迁移。


## 五、两层去重：精确 + 语义

### 5.1 精确去重

同一 KB 内，`LOWER(name)` 唯一。新概念名与已有概念名完全一致时，比较 confidence：

- 新 confidence > 旧 confidence → 更新定义、摘要、合并 aliases
- 新 confidence ≤ 旧 → 仅合并 `source_chunk_ids`（标记该概念也出现在这个 chunk）

同时合并 `aliases`：如果新概念把已有概念的别名作为了自己的 name（如已有"NL2SQL"作为"自然语言转SQL"的别名，新的抽取结果 name 就是"NL2SQL"），系统自动判定为同一概念。

### 5.2 语义去重

精确匹配解决不了"质心向量匹配"和"Centroid Matching"是同义词的情况。

语义去重流程：

```
新概念 name + definition → embed_text() → 1024 维向量
    │
    ▼
pgvector cosine_distance 查询同 KB 下最相似概念
    │
    ├── similarity ≥ 0.85 → 合并（更新定义 / 合并 aliases / 合并源 chunk）
    └── similarity < 0.85 → 真正新概念，INSERT
```

阈值 `concept_similarity_threshold = 0.85` 存 `system_config`，可按知识库粒度调整。

### 5.3 两层去重 + 同名去重 + 合并去重的完整决策树

```
新抽取 term
    │
    ▼
同 chunk 内 LOWER(name) 去重 ──→ 跳过
    │
    ▼
同 KB 下 LOWER(name) 查 DB
    │
    ├── 命中 → confidence 更高? ──→ 更新定义
    │          confidence 更低? ──→ 仅合并 source_chunk_ids
    │
    └── 未命中 → embed(name + definition)
                    │
                    ▼
              pgvector cosine 查同 KB 最相似概念
                    │
                    ├── sim ≥ 0.85 → 合并（更新 / 合并别名）
                    └── sim < 0.85 → INSERT（savepoint 隔离）
                                        │
                                   IntegrityError? → 重新查 DB，二次合并
```


## 六、增量提交：大文档不白干

这是工程上的一个关键决策。早期的实现在所有 chunk 处理完后一次性 commit，结果是：1000 个 chunk 的文档导入，第 998 个报错导致全部回滚，前面 997 个 chunk 的概念全丢了。

改为**逐 chunk commit**：

```python
for ch in chunks:
    # ... 抽取 + 去重 + 写入 ...

    # 每个 chunk 后立即 commit，概念增量可见
    try:
        await db.commit()
    except Exception:
        await db.rollback()
        # 单个 chunk 失败不影响其他
        continue
```

代价：commit 次数从 1 次变为 N 次（每次 ~5-15ms）。收益：导入 1000 个 chunk，即使第 500 个出错，前 499 个的概念不会丢失。

Savepoint 用于隔离单条 INSERT 的 IntegrityError（同名并发插入），只回滚这一条，不回滚整个 chunk。


## 七、RAG 上下文注入

### 7.1 注入时机

在 `chat_service._build_context()` 中，检索完成拿到 Top-K chunk 后，立即查询这些 chunk 关联的概念：

```python
chunk_ids = [chunk.id for chunk in retrieved_chunks]
concepts = await get_concepts_for_chunks(db, chunk_ids, max_concepts=5)
```

### 7.2 注入格式

注入到 System Prompt 的独立小节：

```
## 相关领域术语
以下是本知识库中与检索内容相关的领域术语定义，请在回答中正确使用：

- **质心向量匹配**：KB 内所有 chunk embedding 的算术均值，与用户问题的 embedding
  做余弦距离，取最近 KB 作为路由目标。时间复杂度 O(1)，<1ms。
- **gap 规则**：Layer 1 前两名距离差 < 阈值时放弃质心结果，降级到 Layer 2 LLM
  路由。防止内容重叠 KB 的误判。

（以上定义来自知识库文档，回答时请基于这些定义理解术语，但不需逐字引用定义来源）
```

### 7.3 为什么不把概念放在 User Prompt

System Prompt 是 LLM 的行为指令层，User Prompt 是用户输入层。术语定义是"背景知识"而非"用户指令"，放在 System Prompt 更符合语义角色。实测中放在 System Prompt 的引用率（LLM 回答中准确使用术语定义的比率）显著高于 User Prompt。


## 八、前端交互

### 8.1 概念管理页

入口：`/kb/manage` → 数据治理 → 概念管理 tab。

功能矩阵：

| 操作 | 路径 | 说明 |
|------|------|------|

| 详情查看 | `GET /api/v1/kb/concepts/{id}` | 完整定义 + 引用 chunk 列表 + 相关概念 |

### 8.3 词边界匹配

`renderWithConcepts()` 函数负责在聊天文本中识别概念术语。匹配策略：

1. **术语来源扩展**：不只匹配 `name`，还匹配所有 `aliases`。对于复合名如"自然语言转SQL (NL2SQL)"，自动拆分为"自然语言转SQL""NL2SQL"两个独立术语
2. **长度降序排列**：优先匹配长术语，避免"向量匹配"吞掉"质心向量匹配"的前缀
3. **词边界正则**：术语前后不能是字母/数字/中文字符，防止"SQL"匹配到"MySQL"的内部子串

```typescript
// 构建正则 — 要求词边界
const escaped = allTerms.map(t => t.replace(/[.*+?^${}()|[\]\\]/g, "\\$&"));
const pattern = new RegExp(`(${escaped.join("|")})`, "gi");
const parts = text.split(pattern);
```


## 九、数据库改动

```sql
-- 概念主表
CREATE TABLE kb_concepts (
    id BIGSERIAL PRIMARY KEY,
    kb_id BIGINT NOT NULL REFERENCES kb_knowledge_bases(id) ON DELETE CASCADE,
    name VARCHAR(200) NOT NULL,
    aliases VARCHAR(100)[],            -- PostgreSQL ARRAY
    definition TEXT NOT NULL,
    summary VARCHAR(500),
    embedding vector(1024),            -- pgvector，用于语义去重
    source_chunk_ids BIGINT[],          -- 来源 chunk ID 数组
    status VARCHAR(20) NOT NULL DEFAULT 'auto',  -- auto/confirmed/edited/manual
    confidence FLOAT NOT NULL DEFAULT 0.0,
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- chunk ↔ concept 多对多关联表
CREATE TABLE kb_chunk_concepts (
    id BIGSERIAL PRIMARY KEY,
    chunk_id BIGINT NOT NULL REFERENCES kb_chunks(id) ON DELETE CASCADE,
    concept_id BIGINT NOT NULL REFERENCES kb_concepts(id) ON DELETE CASCADE,
    relevance FLOAT NOT NULL DEFAULT 1.0,  -- 该术语在此 chunk 中的相关度
    position INTEGER[],                     -- 术语在 chunk 中的字符偏移位置（前 10 个）
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE(chunk_id, concept_id)
);

-- system_config 新增概念配置列
ALTER TABLE system_config
    ADD COLUMN concept_extraction_enabled BOOLEAN NOT NULL DEFAULT true,
    ADD COLUMN concept_min_chunk_length INTEGER NOT NULL DEFAULT 500,
    ADD COLUMN concept_max_per_round INTEGER NOT NULL DEFAULT 5,
    ADD COLUMN concept_summary_max_length INTEGER NOT NULL DEFAULT 200,
    ADD COLUMN concept_similarity_threshold FLOAT NOT NULL DEFAULT 0.85;
```


## 十、与智能路由的协同

概念模块和智能路由模块不是孤立的。KB 智能路由的 Layer 2（LLM 语义路由）在构建 KB 描述时，会**自动拼接该 KB 下的概念标签**：

```python
# 智能路由 Layer 2 的 KB 描述构建
kb_descriptions.append(
    f"KB「{kb.name}」: {kb.description or ''}"
    f"概念标签: {', '.join(kb.concept_names[:10])}"  # ← 来自概念抽取
)
```

这意味着：
- 概念越丰富，KB 路由准确率越高
- 用户不需要同时手动维护 KB 描述和术语表
- 概念抽取给路由系统提供了免费的特征工程

两个模块共同构成了 mindvaults 的数据治理闭环：**概念模块让 AI 理解你的内容，路由模块让 AI 找到正确的内容。**
