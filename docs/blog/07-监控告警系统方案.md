# 监控告警系统：把日志变成可观测的看板

> mindvaults 是一个本地私有化的 RAG 知识库。本文记录监控告警系统的技术方案——如何为知识库治理全链路提供统一的埋点、指标看板和告警能力，让系统运行状态不再是黑盒。

## 一、问题：系统在跑，但谁在看？

mindvaults 已经上线了智能路由、对话知识沉淀、Skill 集成、概念术语关联、健康中心等治理模块。每个模块都有自己的日志输出——`logger.info()`、`logger.error()`。但日志是"事后排查"工具：出问题了 `grep` 一把，没问题就没人看。

**核心矛盾：系统有日志但不可观测。你不知道路由命中率在下降、不知道 LLM 调用在变慢、不知道提炼任务是否成功——直到用户反馈"最近检索不太准"。**

问自己几个问题：
- 今天质心命中率多少？是上升还是下降？
- LLM 路由调用耗时多少？有慢调用吗？
- 昨天提炼了几条知识点？失败了几个？
- 外部推送有没有被拦截？

这些问题答案都在日志里，但需要手动查——等于不可用。

## 二、设计哲学：日志归日志，事件归事件

```
日志  → grep 一行定位，排查单次问题用，详情保留
事件表 → SQL 聚合查询，看趋势/告警用，只存聚合数据
```

一套系统，两条通路：

| | 日志（loguru → 文件） | 事件表（PostgreSQL `kb_monitor_events`） |
|---|---|---|
| 用途 | 单次排查，开发者调试 | 趋势分析，看板展示，告警触发 |
| 查询方式 | `grep` / `tail -f` | `SELECT ... GROUP BY ... ORDER BY` |
| 保留周期 | 30 天滚动 | 长期保留，可归档 |
| 数据粒度 | 完整上下文 | category / event / status / 数值 / 简要消息 |

不替换日志，不重复存储。日志保留细节（堆栈、请求体），事件表只存结构化聚合字段（category、event、kb_id、status、value_float、message）。

## 三、一张表承载全部事件

```sql
CREATE TABLE kb_monitor_events (
    id            BIGSERIAL PRIMARY KEY,
    category      VARCHAR(20) NOT NULL,     -- routing / insight / external / concept / health / system
    event         VARCHAR(50) NOT NULL,     -- centroid_hit / llm_route_failed / insight_extracted / ...
    kb_id         INTEGER,
    session_id    VARCHAR(36),
    value_int     INTEGER,                  -- 整数指标（条数、次数）
    value_float   FLOAT,                    -- 浮点指标（距离、置信度、耗时秒）
    status        VARCHAR(20) DEFAULT 'success',  -- success / failed / warning
    message       VARCHAR(500),
    extra_json    JSONB DEFAULT '{}',       -- 扩展字段
    resolved_at   TIMESTAMPTZ,              -- 告警解除时间，NULL=未解除
    created_at    TIMESTAMPTZ DEFAULT NOW()
);
```

为什么不用多张表？五个模块六个分类，如果每个模块一张表，就是 5 张结构相似的表。合并成一张后：

- 常用查询字段（category/event/kb_id/status/value_int/created_at）都是平铺列，不走 JSONB
- 写入低频：路由 1 次/提问 + 提炼 1 次/天 + 扫描 1 次/周
- 每天 1000 次提问 × 200 字节 ≈ 200KB，存储无压力

`extra_json` 只存无法预统一的扩展字段（如健康扫描的重复组数量、外部推送的平台标识），不参与常用过滤条件。

告警的解除没有用单独的"告警表"，而是直接在事件行上加 `resolved_at` 字段——解除告警就是 `UPDATE SET resolved_at = NOW()`。

## 四、事件定义：让每个模块都能被观测

### 4.1 智能路由（`category = 'routing'`）

```
用户提问
  │
  ├── centroid_hit   → 质心命中，记录 distance
  ├── centroid_gap   → 前两名太接近，降级 Layer 2
  ├── llm_route_hit  → LLM 路由命中，记录 confidence
  ├── llm_route_miss → LLM 路由低置信度，降级 Layer 3
  ├── llm_route_failed → LLM 调用异常（网络超时/API 故障）
  └── route_fallback → 进入 Layer 3 用户引导
```

关键指标：**质心命中率**（越高越好）、**LLM 路由率**（越低越好，说明 Layer 1 够强）、**降级率**（越低越好）。

### 4.2 LLM 调用（`category = 'system'`）

每次 `generate_stream` 完成后写入 `llm_call_completed`，记录：

| 字段 | 含义 |
|------|------|
| `value_float` | 调用耗时（秒） |
| `value_int` | 估算 token 数 |
| `extra_json.input_tokens` | 输入 token 估算 |
| `extra_json.output_tokens` | 输出 token 估算 |
| `extra_json.model` | 模型名称 |

失败时写入 `llm_generation_failed`（status=failed），Embedding 失败写 `embedding_failed`，Reranker 降级写 `rerank_failed`。

### 4.3 对话知识沉淀（`category = 'insight'`）

批处理生命周期：

```
insight_batch_started → insight_batch_completed
                         ├── extracted=N, errors=M
                         └── status=warning（errors > 0 时）
```

后台单条提炼失败写 `insight_llm_failed`，异常崩溃写 `insight_bg_processing_failed`。

### 4.4 概念术语关联（`category = 'concept'`）

```
concept_extraction_completed
  value_int = 新增+更新的概念数
  extra_json.chunks = 处理的 chunk 数
```

单 chunk LLM 失败写 `concept_extraction_failed`，入库失败写 `concept_commit_failed`。

### 4.5 健康扫描（`category = 'health'`）

```
health_scan_started
  → detect_duplicates / detect_low_quality / detect_outdated
    / detect_orphans / detect_fragment_clusters
  → health_scan_completed (value_float = health_score, extra_json = 各维度计数)
    
异常路径：
  → health_scan_failed (检测过程异常)
```

### 4.6 外部推送（`category = 'external'`）

```
external_push_received
  value_int = 接收条数
  extra_json.platform = claude_code
  extra_json.skipped = 去重跳过
  extra_json.rejected = 质量门拦截
```

### 4.7 文档摄入（`category = 'system'`）

```
doc_uploaded → doc_ingestion_completed (value_int = chunk 数)
             → doc_ingestion_failed (status = failed)
```

## 五、看板：从数字到直觉

看板布局的核心思路：**告警最小化、指标一眼看清、趋势有上下文**。

```
┌─ 告警折叠条 ───────────────────────────────────────┐
│ 🔴 3 条活跃告警 [路由2] [概念1] 展开 ▸               │  默认占 1 行
└──────────────────────────────────────────────────────┘

┌──────────┬──────────┬──────────┬──────────┐
│ 路由次数  │ 质心命中率 │ LLM 路由率 │  降级率  │         路由指标卡
│  156 ↑   │   85% →  │   12% →  │   3%  ↓  │
├──────────┼──────────┼──────────┼──────────┤
│ LLM 调用 │ 平均耗时  │ Token 消耗 │ LLM 可用率 │        LLM 调用指标
│  1,247   │  1.8s    │   486K    │  99.7%   │
└──────────┴──────────┴──────────┴──────────┘

┌─ 路由效果趋势（近 7 天）──┐  ┌─ Token 用量趋势 ──┐
│  📈 Recharts 面积图      │  │  📊 堆叠柱状图     │
└───────────────────────────┘  └──────────────────┘

┌─ LLM 耗时分布 ──┐  ┌─ KB 匹配热度 ────────────┐
│  分桶直方图      │  │  Python 技术文档  68 ████ │
│  <1s 623        │  │  产品 PRD         45 ███  │
│  1-2s 345       │  │  运维手册         38 ██   │
│  2-4s 198       │  └──────────────────────────┘
│  4-8s 78        │
│  >8s 3 ⚠️       │
└─────────────────┘

┌─ 系统事件（近 24h）────┐  ┌─ 提炼 & 概念（本周）─┐
│ ✅ 外部推送 45   ❌ 2   │  │  提炼     12 条      │
│ ✅ 概念抽取 12   ❌ 0   │  │  新概念    8 个      │
│ ✅ 健康扫描 1    ❌ 0   │  │  健康得分  78%      │
│ ✅ 知识提炼 12   ❌ 0   │  │  待处理    6 条      │
└────────────────────────┘  └──────────────────────┘
```

设计细节：
- **告警默认折叠**，顶部一条："N 条活跃告警 [分类计数] 展开 ▸"，不挡指标卡
- **趋势图用面积图**，比折线图更有"量感"，颜色与指标卡一致
- **耗时分布用分桶直方图**，颜色从绿→黄→橙→红，慢调用一眼可见
- **KB 热度用横向进度条**，最大的一项满宽，其余按比例缩放
- **暗色背景**呼应侧边栏 slate-900，指标卡在深色背景上有"操作台"质感

图表库选 Recharts 而非 ECharts——看板的图表需求不复杂（折线 + 柱状 + 进度条），Recharts 的声明式 React API 和 Tailwind 搭配自然，150KB 体积远小于 ECharts 的 1MB。

## 六、告警机制

### 6.1 告警规则（存在 `system_config` 中）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `alert_llm_route_fail_threshold` | 3 | LLM 路由连续失败 N 次告警 |
| `alert_fallback_rate_threshold` | 0.20 | Layer 3 降级率超过 20% 告警 |
| `alert_centroid_fail` | true | 质心计算失败立即告警 |
| `alert_external_push_fail` | true | 外部推送失败立即告警 |
| `alert_insight_batch_fail` | true | 提炼批处理失败告警 |
| `alert_health_scan_fail` | true | 健康扫描失败告警 |
| `alert_concept_extraction_fail` | true | 概念抽取失败告警 |
| `alert_slow_call_threshold` | 5.0 | LLM 慢调用阈值（秒） |

规则检查 API `GET /api/v1/kb/monitor/alerts` 每次被调用时实时执行：查最近连续失败次数、算降级率、查各即时失败开关。

### 6.2 告警呈现

不搞弹窗、不搞强提醒。告警出现在看板顶部：
- 折叠状态：一行摘要（"3 条活跃告警 [路由2] [概念1]"）
- 展开后：紧凑单行列表，hover 显示 ✕ 解除按钮
- 全部已读：一键 `POST /api/v1/kb/monitor/alerts/resolve-all`

**页面内告警先上，Webhook**（钉钉/飞书/企业微信）**留作后续扩展**。

## 七、埋点策略：不侵入业务逻辑

埋点的核心挑战：在不污染业务代码的前提下，在正确的时机写入正确的事件。

### 原则

```
路由               → 在路由函数内部写（kb_router），不在 chat_stream 里重复
LLM 调用            → 在 chat_stream 的生成循环结束后写
批处理               → 在 insight_service 的开始/结束/异常处写
外部接口             → 在 external_push_service 的处理结束时写
```

### 一处容易踩的坑

`write_event()` 只调 `db.flush()` 不调 `db.commit()`——因为业务代码在之后还会继续操作，需要在同一个事务中。但 `chat_stream` 是 async generator，中间有多个 `yield` 点。如果 `yield` 之后客户端断开或异常导致 `return`，事务被回滚，前面的 `flush` 全丢。

最典型的场景：**新会话 + 路由失败**。`session=None` 时 fallback 路径直接 `return` 不 commit，导致前面写的路由事件全部丢失。

修复方法是确保所有 `return` 分支都有 `db.commit()`（或 `db.rollback()`）：

```python
if session is None:
    # 尚未创建 session，但需要 commit 监控数据
    await db.commit()
    return
```

## 八、待优化

- [ ] **真实 token 计数**：当前用文本长度 / 3 估算，接入 LLM API 返回的 `usage` 字段可获精确值
- [ ] **Webhook 告警推送**：支持钉钉/飞书/企业微信，告警条件触发时主动推送
- [ ] **自定义时间范围**：看板目前固定"今日/近 7 天/近 24h"，应支持用户选择日期范围
- [ ] **告警静默期**：夜间定时任务的正常失败（如 LLM 服务维护窗口）不应触发告警
- [ ] **事件归档**：`kb_monitor_events` 长期增长，需要按时间分区或定期归档
- [ ] **邮件/手机通知**：严重告警（如 LLM 可用率 < 90%）应支持邮件通知
