# 知识库健康中心：从退化到自愈的治理闭环

> mindvaults 是一个本地私有化的 RAG 知识库。本文记录知识库健康中心的技术方案——如何像体检一样诊断知识库的退化，在数据腐烂之前主动干预。

## 一、问题：知识库不是存进去就完了

大多数 RAG 产品把"摄入成功"当作终点。文档解析了、切片了、向量化了——任务完成。

但真实使用中，知识库每天都在退化：

| # | 退化类型 | 现象 | 后果 |
|---|---------|------|------|
| 1 | **碎片化** | 同一知识点散落在多个 chunk（来自不同文档/insight），检索命中随机 | 用户每次得到的答案质量不稳定 |
| 2 | **低质量** | 短 chunk、空壳内容占据检索位 | 好内容被挤出 top_k，检索精度下降 |
| 3 | **过时** | 旧版本、已废弃的信息仍在库中 | LLM 引用过时内容，给出错误建议 |
| 4 | **孤岛** | chunk 的源文档已删除但未清理，或 insight 被拒绝但 chunk 还在 | 幽灵数据污染检索结果 |

这不是 bug，是系统动力学。知识库越大、更新越频繁，退化越快。**不做治理的知识库，半年后检索命中率可以腰斩。**

核心矛盾：**RAG 系统有摄入、有检索、有生成，但没有"体检"——用户不知道自己的知识库有多健康，也不知道该修哪里。**

## 二、设计哲学：诊断 + 决策，不搞黑盒自动化

动手之前我们先定了一个原则：**诊断报告 + 用户决策**。系统检测问题并推荐方案，用户确认后执行。

不做全自动处理的原因很简单：两个 chunk 相似度 0.95，到底是不是真的重复？LLM 判断不了。用户看一眼内容就知道了。自动化越激进，误杀率越高。

唯一的例外：相似度 > 0.98 且双方都来自同一文档 → 自动合并，保留质量高的那一个。这个区间的准确率接近 100%，误杀风险可忽略。

## 三、五维检测

每次健康扫描跑五个检测器，各自独立，并行执行。

### 3.1 近重复检测

pgvector 自连接，一次 SQL 完成：

```sql
SELECT c1.id, c2.id, 1 - (c1.embedding <=> c2.embedding) AS sim
FROM kb_chunks c1, kb_chunks c2
WHERE c1.kb_id = :kb_id
  AND c2.kb_id = :kb_id
  AND c1.id < c2.id
  AND 1 - (c1.embedding <=> c2.embedding) > :threshold  -- 默认 0.92
ORDER BY sim DESC;
```

相似度分三层处理：

| 区间 | 相似度 | 处理方式 |
|------|:--:|------|
| 极高 | > 0.98，同文档 | 自动合并（保留优者） |
| 高 | 0.92-0.98，不同来源 | 推荐 merge，用户选择 |
| 中 | 0.85-0.92 | 标记"主题相近"，建议链接 |

相似对用连通分量（Connected Components）算法聚合成重复组，每组推荐一个质量分最高的 chunk 作为保留项。

### 3.2 低质量检测

```sql
SELECT id, content, LENGTH(content) AS len
FROM kb_chunks
WHERE kb_id = :kb_id
  AND LENGTH(content) < :min_length;  -- 默认 100
```

额外规则：
- 纯标点/数字占比 > 50% → 低质量
- 内容全是代码块但没有说明文字 → 低质量
- insight 被拒绝但关联 chunk 仍在 → 低质量

### 3.3 过时检测

三个信号：

| 信号 | 检测方式 | 示例 |
|------|---------|------|
| 旧版本号 | 正则匹配 | `Python 2.7`、`Django 1.x`、`React 15` |
| 文档新版本 | 同一 doc_name 有更新文档上传，旧 chunk 时间戳早于新文档 | 上传了 v2.md，v1.md 的 chunk 标记过时 |
| 时间衰减 | chunk 创建 > 1 年且从未被检索命中 | `hit_count = 0 AND age > 365 days` |

### 3.4 孤岛检测

```sql
-- chunk 关联的文档已被软删除
SELECT c.id FROM kb_chunks c
JOIN kb_documents d ON c.document_id = d.id
WHERE d.deleted_at IS NOT NULL;

-- insight chunk 对应的 insight 已被拒绝
SELECT c.id FROM kb_chunks c
JOIN kb_insights i ON c.source_insight_id = i.id
WHERE i.status = 'rejected';
```

### 3.5 碎片簇检测

主题相近但不重复的一组 chunk，建议用户手动定义主题簇。当一个检索命中簇内任意 chunk 时，附带展示簇内其他内容标题。

```
检测到 6 个 chunk 围绕"Django ORM 性能优化"：
  chunk_A: "Django ORM 的 select_related..."
  chunk_B: "优化 Django 查询：prefetch_related..."
  chunk_C: "ORM 查询次数过多？用 django-debug-toolbar..."
  ...

推荐：创建主题簇「Django ORM 性能优化」，一键链接这 6 个 chunk
```

## 四、健康评分

每个维度扣分，算出综合健康分（0-100），类似信用分：

```python
def _compute_health_score(total_chunks, dup_count, low_quality, outdated, orphan):
    penalties = {}
    penalties["duplicates"]    = min(dup_count * 2, 25)    # 每个重复组 -2，上限 -25
    penalties["low_quality"]   = min(low_quality * 1, 15)  # 每个低质量 -1，上限 -15
    penalties["outdated"]      = min(outdated * 0.5, 10)   # 每个过时 -0.5，上限 -10
    penalties["orphans"]       = min(orphan * 2, 10)       # 每个孤岛 -2，上限 -10

    total_penalty = sum(penalties.values())
    return max(0.0, 100.0 - total_penalty), penalties
```

扣分上限防止某个维度爆炸导致分数归零失去参考意义。扣分明细在报告中可见，用户知道该优先修什么。

## 五、处理操作

### 5.1 合并重复

用户在健康报告中看到一条推荐：

```
🔄 疑似重复 (12 组)

组 1: "GIL 限制及解决方案" 重复度 0.96
  ○ chunk_A (文档: python_guide.md, 300字, 质量分 0.82)
  ○ chunk_B (insight: GIL解决方案, 250字, 质量分 0.70)
  ○ chunk_C (文档: faq.md, 180字, 质量分 0.55)

  → 推荐保留: chunk_A (质量分 0.82)
  → 其余物理删除

  [采纳推荐]  [选 chunk_B]  [选 chunk_C]
```

点击"采纳推荐"后，系统物理删除 chunk_B 和 chunk_C，更新文档 `chunk_count`。注意——**原文不受影响**，用户在文档管理页面随时可以重索引恢复切片。这和"软删除"不同：既然原文可恢复，就不需要保留冗余的向量数据。

### 5.2 清理孤岛

一键物理删除所有孤岛 chunk。同样，源文档还在就可以重索引恢复。

### 5.3 归档低质量

物理删除低质量切片。配合后续的文档预处理能力（v0.8），未来摄入的新切片质量会显著提升。

## 六、三维触发

| 时机 | 条件 | 范围 | 说明 |
|------|------|------|------|
| **摄入时** | 新文档/insight 入库后 | 仅新内容 vs 存量 | 即时提示用户，非阻塞 |
| **定期扫描** | 每周日凌晨 3:00 | 全库 | 生成完整诊断报告 |
| **手动触发** | 用户在健康中心点"立即分析" | 全库或指定范围 | 即时诊断 |

摄入时检测在 `ingestion_service` 中异步执行，不阻塞上传响应。即使检测失败，文档摄入不受影响。

## 八、质量评分模型

合并时选优，需要一个客观的评分标准：

```python
def compute_quality_score(chunk) -> float:
    score = 0.0

    # 1. 内容长度 (0-0.25)
    score += min(len(chunk.content) / 1000, 1.0) * 0.25

    # 2. 引用热度 (0-0.30) — QA 中检索命中次数
    score += min(chunk.hit_count / 20, 1.0) * 0.30

    # 3. 概念关联数 (0-0.20) — 关联的概念越多，信息密度越高
    score += min(concept_count / 5, 1.0) * 0.20

    # 4. 时效性 (0-0.15)
    score += max(0, 1.0 - age_days / 365) * 0.15

    # 5. 来源权威性 (0-0.10) — 已确认 insight > 文档 > 自动 insight
    score += source_weight[chunk.source_type] * 0.10

    return round(score, 4)
```

引用热度权重最高（0.30），这是最直接的"用户投票"——被检索命中越多的 chunk，越可能是好内容。

|-------|--------|---------|
| `health_scan_started` | success | 扫描开始 |
| `health_scan_completed` | success | 扫描完成，记录健康度及各维度数量 |

| `health_orphans_cleaned` | success | 孤岛清理完成 |

## 十、与文档预处理服务的协同

健康扫描是"事后治理"，文档预处理是"源头治理"。两者不是替代关系，而是互补：

```
文档预处理服务 (v0.8)          健康中心 (v0.7)
─────────────────────         ─────────────
Parser → Preprocessor →      定期扫描 → 诊断报告
Chunker → Embedder            → 合并 / 清理 / 归档
    ↑                              ↑
   源头减少碎片                   事后修复存量
```

理想情况下，文档预处理上线后，新摄入的文档碎片量大幅下降，健康扫描主要处理存量问题。两个模块共同构成 mindvaults 的数据治理闭环。

## 十一、待优化

- [ ] **碎片簇的自动主题识别**：当前用 chunk 前 40 字符做标签，可以改为 LLM 提取簇主题名
- [ ] **增量扫描**：大型 KB 全扫一次可能耗时数十秒，改为只扫描上次报告后变更的 chunk
- [ ] **健康趋势图**：前端加历史报告的健康分折线图，可视化 KB 健康状况变化
- [ ] **智能推荐修复优先级**：根据各维度 penalty 占比，自动推荐"先修这个收益最大"
- [ ] **回滚机制**：合并操作支持撤销（当前物理删除不可逆，但原文重索引可恢复）
